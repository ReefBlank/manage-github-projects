# 阶段 2：建仓执行手册

本手册对应四阶段状态机中的「建仓」阶段（第 2/4 阶段）。四阶段固定为 **接入 / 建仓 / 合规 / 发布**，本手册只覆盖第 2 阶段。

进入本阶段的前提是用户已经明确回复「公开范围确认」。本阶段结束时，应得到一个本地干净、忽略规则完备、无敏感信息、体积正常、已完成首次提交并成功推送到远程的仓库。

> 术语统一：四道门禁 =「目标信息收齐」「公开范围确认」「首推范围确认」「发布方案确认」。本阶段负责其中的「首推范围确认」，其余门禁按所处阶段分别处理。

## 阶段目标与完成标准

| 项目 | 完成标准 | 证据等级 |
| --- | --- | --- |
| 本地初始化 | 仓库根目录存在 `.git`，`git rev-parse --is-inside-work-tree` 返回 `true` | L2 本地 Git |
| 身份配置 | `git config user.name` 与 `git config user.email` 均有值且属于用户本人 | L2 本地 Git |
| 忽略规则 | `.gitignore` 已提交，覆盖构建产物、依赖目录、本地环境文件、日志与缓存 | L1 静态 |
| 敏感信息扫描 | 待提交内容中无密钥、token、密码、私钥、连接串与个人数据 | L1 静态 |
| 体积体检 | 无超过约 50 MiB 的单文件；总体积无异常 | L1 静态 |
| 远程仓库 | GitHub 上存在目标仓库，可见性与用户确认一致 | L3 远程 API |
| 首次推送 | 目标分支与提交存在于远程，本地与远程一致 | L2 本地 Git + L3 远程 API |

低等级证据不得冒充高等级：本地 `git log` 里有提交，不等于远程已有该提交。

## 步骤 0：进入前置检查

1. 确认项目根目录绝对路径，记录到项目状态文件。
2. 读取阶段 1 的产出：目标仓库名、归属账号或组织、可见性、许可证、公开范围清单、排除路径清单。缺失任何一项就回到「目标信息收齐」门禁补齐，不得用常见做法替代。
3. 探测环境凭据是否可用，只检查存在性与权限范围，不读取、不回显、不记录凭据本身：

```bash
git config --get credential.helper
gh auth status
ssh -T git@github.com
```

4. 判断本地项目是否已经是 Git 仓库：

```bash
git rev-parse --is-inside-work-tree
git status --short
git remote -v
```

已经是仓库时不要重复初始化，跳到步骤 2 处理忽略规则与体检；已有远程时先报告现有远程配置，再确认是否复用。

## 步骤 1：本地初始化与身份配置

1. 确认或设置提交身份。提交者身份必须是用户本人，不得伪造：

```bash
git config user.name "用户自己的名字"
git config user.email "用户自己的邮箱"
```

读取当前值核对：

```bash
git config user.name
git config user.email
```

2. 确认**默认分支**名。默认使用 `main`；用户所在团队有既定约定时以用户选择为准，并在状态文件中记录。

```bash
git init -b main
```

`git init -b main` 不适用于过旧的 Git 版本；若该命令不可用，先执行 `git init`，再执行 `git branch -M main`。

3. 读取实际输出确认默认分支：

```bash
git branch --show-current
git symbolic-ref --short HEAD
```

4. 在已有仓库中不要执行 `git init` 覆盖用户既有配置；只做只读检查。

## 步骤 2：忽略规则

1. 按实际技术栈生成 `.gitignore`，必须覆盖以下类别：

| 类别 | 示例条目 |
| --- | --- |
| 依赖目录 | `node_modules/`、`venv/`、`__pycache__/` |
| 构建产物 | `dist/`、`build/`、`target/`、`*.pyc` |
| 本地环境文件 | `.env`、`.env.*`、`*.local` |
| 编辑器与系统文件 | `.vscode/`、`.idea/`、`.DS_Store`、`Thumbs.db` |
| 日志与缓存 | `*.log`、`.cache/`、`*.tmp` |
| 凭据与大文件 | 私钥、证书、密钥库、数据导出文件 |

2. 用户明确要提交的最小示例文件（如 `.env.example`）不在排除范围内，但其中只能放占位键名，不能放真实值。
3. 生成后复核是否误伤必要文件：

```bash
git check-ignore -v <路径>
git status --short
```

4. 忽略规则本身要提交进仓库，让后续协作者行为一致。

## 步骤 3：敏感信息扫描（推送前强制）

**敏感信息扫描**是本阶段不可跳过的关卡。命中时必须停下来向用户报告命中位置与建议处置，**不要先推上去再删**。公开是一次不可逆的信息披露，删除历史也无法保证未被缓存或归档。

1. 扫描待提交内容，而不是只扫描工作区。优先使用用户环境已有的工具；工具不可用时按关键词人工核查：

```bash
git add -A --dry-run
git diff --cached --name-only
grep -rInE "(api[_-]?key|secret|password|passwd|token|BEGIN [A-Z ]*PRIVATE KEY|AKIA[0-9A-Z]{16})" .
```

2. 重点检查：`.env` 类文件、CI 配置中的硬编码值、连接串、私有地址与内网域名、真实姓名与联系方式、数据库导出、测试数据中的真实个人信息。
3. 命中处置顺序：
   1. 暂停本次推送，列出行号与文件路径。
   2. 建议先从工作区移除并把该路径加入 `.gitignore`。
   3. 若内容已经进入本地提交历史，说明两种路径：丢弃本地历史（未推送时最简单）或历史重写（见步骤 4 与危险操作边界）。
   4. 若凭据可能已经暴露在别处，建议用户先旋转密钥，再讨论清理。
4. 报告结论必须标注**证据等级**：静态扫描结果属于 L1 静态；本地历史检查属于 L2 本地 Git。

## 步骤 4：体积体检（推送前强制）

**体积体检**用来避免把仓库变成不可克隆的巨石。

1. 统计单文件大小与仓库总体积：

```bash
git ls-files -z | xargs -0 du -h | sort -h | tail -20
du -sh .git
```

2. 判定阈值：

| 情况 | 建议处置 |
| --- | --- |
| 单文件超过约 50 MiB | 必须先与用户确认处置方案 |
| 单文件 10–50 MiB 且为二进制资产 | 提出 **Git LFS** 方案，由用户决定 |
| 构建产物、缓存、数据集被误加入 | 从跟踪列表移除并写入 `.gitignore` |
| 发行包、安装包、压缩包 | 改用 Release 附件而不是提交进仓库 |

3. 若用户选择 **Git LFS**：

```bash
git lfs install
git lfs track "*.psd"
git add .gitattributes
```

启用后必须提交 `.gitattributes`，并提示用户：克隆者需要安装 Git LFS 才能取得完整文件。

4. 若大文件已经进入本地提交历史且体积需要收缩，涉及 **`git filter-repo`** 的历史重写：这是危险操作，必须走「危险操作单项授权」流程，先说明目标、影响范围（所有提交哈希都会改变）、不可逆后果与备份方式（推荐先 `git clone --mirror` 做完整备份），得到用户对该项操作的单独授权后再执行。未推送时首选更简单的做法：删除包含大文件的提交并重新提交。

## 步骤 5：首次提交

1. 按逻辑分组暂存，不要把互不相关的改动塞进一个提交：

```bash
git add .gitignore README.md
git add src/
git commit -m "chore: 初始化仓库结构"
```

2. 提交信息遵循提交规范（**Conventional Commits**），细则见 [maintenance.md](maintenance.md)。
3. 不得伪造提交者身份，不得改写用户已有的提交历史。
4. 提交后核对将进入远程的实际内容：

```bash
git log --oneline -10
git show --stat HEAD
git ls-files
```

5. 逐项对照阶段 1 的公开范围清单，确认没有多出未确认的路径。

## 步骤 6：创建远程仓库

**创建远程仓库**属于建立远程资源，必须在「公开范围确认」之后执行。

1. 先查询**同名仓库**是否存在，命中时停下来问用户是复用还是改名，不要盲目创建：

```bash
gh repo view <owner>/<repo> --json name,visibility,defaultBranchRef
```

2. 优先使用用户环境中已登录的 CLI 创建：

```bash
gh repo create <owner>/<repo> --public --description "一句话简介" --source . --remote origin
```

3. CLI 不可用时，给出网页端编号步骤，由用户完成，代理不代替用户登录或授权：
   1. 打开 GitHub 首页右上角 `+` 菜单，选择 `New repository`。
   2. 填写仓库名与描述，选择可见性。
   3. **不要**勾选自动创建 README、`.gitignore` 或 LICENSE，避免与本地已有文件冲突。
   4. 创建后复制 HTTPS 或 SSH 地址。
4. 创建后立即核验可见性与默认分支：

```bash
gh repo view <owner>/<repo> --json visibility,defaultBranchRef,url
```

5. 归属账号、仓库名、可见性与阶段 1 确认不一致时，停止后续步骤并回到用户确认。

## 步骤 7：首次推送（首推范围确认门禁）

1. 添加远程并核对：

```bash
git remote add origin <远程地址>
git remote -v
```

远程已存在时使用 `git remote set-url origin <远程地址>`，不要重复添加。

2. 向用户给出将推送内容的摘要：分支名、提交数量、文件数量、被排除项、是否存在远程已有内容。等待用户明确回复「**首推范围确认**」。
   - 「下一步」「好的」「可以」「开始吧」等泛化回复不等于通过门禁。
   - 用户只回复泛化词时，重复当前门禁和待确认项，不得推进。
3. 确认后执行首次推送：

```bash
git push -u origin main
```

分支名以步骤 1 确认的默认分支为准，**默认分支**通常为 `main`。

4. 远程已经存在提交（例如用户先前用网页初始化过）而本地历史不同时，禁止使用 `force push` 覆盖。此时停下来说明冲突，给出两种方案：拉取合并远程历史，或在用户对具体目标执行「危险操作单项授权」后由用户决定是否覆盖。

## 步骤 8：推送后核验

1. 本地与远程双重核验：

```bash
git status
git log --oneline -3
git rev-parse HEAD
gh repo view <owner>/<repo> --json defaultBranchRef,visibility
gh api repos/<owner>/<repo>/commits --jq '.[0].sha'
```

本地用 `git status` 确认工作区干净、没有未跟踪的待推送文件；远程用 API 确认分支与可见性。

2. 本地 HEAD 与远程分支 HEAD 必须一致。本地状态属于 L2 本地 Git，远程 API 返回属于 L3 远程 API，两者不能互相替代。
3. 汇报格式固定包含：当前阶段（建仓，第 2/4 阶段）、已完成事实、远程仓库地址、默认分支、可见性、证据等级、唯一下一步（进入合规阶段）。

## 门禁与危险操作边界

| 边界 | 规则 |
| --- | --- |
| 「首推范围确认」 | 未收到用户明确回复前，不执行 `git push`，不添加远程之外的远程资源 |
| 「公开范围确认」 | 未通过前不创建公开仓库、不推送任何内容 |
| 「目标信息收齐」 | 仓库名、归属、可见性、许可证未知时不初始化、不建仓 |
| 危险操作单项授权 | `git filter-repo` 等历史重写、`force push`、删除仓库、更改可见性、删除 tag 或 Release，必须逐项单独说明目标、影响、不可逆后果与备份方式，并取得用户对该项的单独授权 |
| 一次授权范围 | 一次授权只对当次、当个目标有效，不自动扩展到其他危险操作，也不构成长期授权 |
| 扫描与体检 | **敏感信息扫描**与**体积体检**属于推送前强制关卡，任何一项未完成都不得推送 |
| 泄漏应对 | 发现疑似泄漏先报告并建议轮换密钥，再讨论历史清理 |

## 常见情况处置

| 情况 | 处置 |
| --- | --- |
| 误提交了 `.env` 且尚未推送 | 取消暂存、加入 `.gitignore`、重新提交 |
| 误提交了 `.env` 且已推送 | 立即报告，建议旋转所有相关密钥；历史清理作为独立危险操作走单项授权 |
| 本地与远程历史无关 | 停止推送，说明冲突，让用户选择合并或覆盖 |
| 单文件 200 MiB 的模型权重 | 建议改用 Release 附件或 Git LFS，由用户选择 |
| 用户要求直接公开私有内容 | 复述公开范围与不可逆后果，取得「公开范围确认」后再继续 |
| Git 未安装或版本过旧 | 只报告缺失能力与影响，引导用户安装，不代替用户执行系统级安装 |
