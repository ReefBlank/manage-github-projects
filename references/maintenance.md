# 日常维护手册

本手册覆盖四阶段状态机中「发布」之后的持续维护动作，也覆盖合规阶段的社区协作部分。四阶段固定为 **接入 / 建仓 / 合规 / 发布**；维护工作可随时与合规、发布交错推进，但门禁不得跳过。

维护目标是让仓库长期可读、可贡献、可交接：提交历史可追、分支规则明确、issue 与 pull request 有归属、依赖风险可控、失效项目体面下线。

> 证据等级 = L1 静态 / L2 本地 Git / L3 远程 API / L4 CI / L5 发布物。维护结论必须标注来源。

## 维护动作总览

| 类别 | 动作 | 推荐频率 | 证据等级 |
| --- | --- | --- | --- |
| 提交 | 遵循 Conventional Commits 提交规范 | 每次提交 | L2 本地 Git |
| 分支 | 执行分支策略，保护默认分支 | 常驻 | L3 远程 API |
| 协作 | 处理 issue 与 pull request | 每周 | L3 远程 API |
| 组织 | 维护标签与里程碑 | 每月 | L3 远程 API |
| 依赖 | 审核依赖更新，启用 Dependabot | 每月 | L3 远程 API + L4 CI |
| 安全 | 检查敏感信息与安全策略 | 每月 | L1 静态 |
| 归属 | 维护 CODEOWNERS 与维护者名单 | 每季度 | L3 远程 API |
| 终结 | 归档不再维护的仓库 | 一次 | L3 远程 API |

## 提交规范

1. 使用 **Conventional Commits** 格式，**提交规范**全仓库统一：

```text
<类型>(<可选范围>): <简短描述>

<可选正文：为什么这样改>

<可选脚注：BREAKING CHANGE、关联 issue>
```

2. 常用类型：

| 类型 | 含义 | 是否影响版本号 |
| --- | --- | --- |
| `feat` | 新增功能 | MINOR |
| `fix` | 修复缺陷 | PATCH |
| `docs` | 只改文档 | 无 |
| `refactor` | 重构且行为不变 | 无 |
| `perf` | 性能优化 | PATCH |
| `test` | 测试相关 | 无 |
| `build` | 构建或依赖 | 无 |
| `ci` | 工作流改动 | 无 |
| `chore` | 杂项 | 无 |
| `revert` | 回滚提交 | 视内容而定 |

3. 破坏性变更用 `!` 或脚注标记，并在正文写迁移方式：

```text
feat(api)!: 移除 v1 分页参数

BREAKING CHANGE: page 参数被 cursor 取代，旧参数将在两个版本后报错。
```

4. 提交信息用祈使句描述结果，说明「为什么」而不是重复 diff 内容。
5. 每次提交只做一件事；不把格式化改动与逻辑改动混在一起。
6. 不伪造提交者身份，不改写他人已推送的历史。
7. 检查最近提交是否合规：

```bash
git log --oneline -20
git log --format="%h %s" -20
```

## 分支策略

1. 默认采用最小可用的**分支策略**，避免规则超出个人项目的实际需要：

| 分支 | 用途 | 规则 |
| --- | --- | --- |
| `main` | 稳定线，随时可发布 | 禁止直接推送，需 PR 或本地校验后推送 |
| `feat/*` | 功能开发 | 从 `main` 切出，合并后删除 |
| `fix/*` | 缺陷修复 | 从 `main` 切出，合并后删除 |
| `release/*` | 需要冻结的发布准备 | 只在多版本并行时使用 |

2. 个人项目的推荐做法：小改动直接在 `main` 上以合规提交推进；涉及重构或多步改动时开短期分支，合并后清理。
3. 分支保护：为 `main` 开启保护，至少包含「禁止强制推送」「禁止删除分支」「合并前需通过状态检查」。

```bash
gh api -X PUT repos/<owner>/<repo>/branches/main/protection \
  --input branch-protection.json
```

4. 分支保护属于仓库设置变更：能用 API 完成就做，不能则由用户在弹出的网页界面完成，并说明为什么需要。改可见性、改默认分支这类设置变更若属危险范畴，按下面的危险操作边界处理。
5. 定期清理已合并的远程分支：

```bash
git branch --merged main
git push origin --delete <已合并分支>
```

## issue 处理

1. 先确保仓库有 Issue 模板（`bug_report` 与 `feature_request`），让报告包含复现步骤、期望行为、实际行为、环境信息。
2. 收到 **issue** 后的处理顺序：
   1. 分类：缺陷 / 功能请求 / 疑问 / 文档 / 重复 / 无效。
   2. 打标签并（如需要）指派里程碑。
   3. 无法复现时，用编号清单向报告者索取最小复现与版本号。
   4. 有明确结论后在 issue 中说明处置，再关闭，不要静默关闭。
3. 对安全类报告，引导使用 `SECURITY.md` 中的私密渠道，不在公开 issue 中要求提供密钥或漏洞利用细节。
4. 批量关闭 issue 属于危险操作，必须逐项说明范围并取得单项授权；能逐条处理就不要批量处理。

## pull request 处理

1. 仓库需有 PR 模板，列出：改动目的、验证方式、是否破坏兼容、关联 issue。
2. 收到 **pull request** 后的检查顺序：

| 检查项 | 通过标准 |
| --- | --- |
| 变更范围 | 与描述一致，无无关文件或格式化噪音 |
| 测试 | 新增或修改行为有对应测试，CI 通过 |
| 依赖 | 未引入不必要的依赖或变更锁文件范围过大 |
| 安全 | 无硬编码凭据、无来源不明的二进制文件 |
| 文档 | 用户可见变化已更新 README 或 CHANGELOG |
| 许可 | 新增第三方代码保留其许可证与出处 |

3. 提交者身份与提交信息符合提交规范；不合规时给出具体修改建议，而不是重写对方历史。
4. 合并方式由用户或维护者决定：个人项目推荐 squash 合并以保持 `main` 线性；合并后删除来源分支。
5. **不得代替用户提交**或替代用户做出产品与法律判断；代理可以准备补丁、检查清单与建议措辞，但最终的推送、合并、关闭与发布动作由用户确认。
6. 核验合并结果属于 L3 远程 API；工作流是否通过属于 L4 CI。

## 标签与里程碑

1. **标签**用于分类，保持数量可控，命名统一小写短横线：

| 类别 | 示例 |
| --- | --- |
| 类型 | `bug`、`enhancement`、`documentation`、`question` |
| 状态 | `needs-repro`、`blocked`、`good first issue` |
| 优先级 | `priority:high`、`priority:low` |

2. **里程碑**用于聚合一个版本或一个阶段的工作，名称与版本号对应，例如 `v1.5.0`。
3. 发布完成后关闭对应里程碑，并把未完成项移到下一个里程碑，写明去向。
4. 不要用标签代替文档：约定与规则写进 `CONTRIBUTING.md`。

```bash
gh label list
gh issue list --label bug --state open
gh api repos/<owner>/<repo>/milestones --jq '.[] | .title, .open_issues'
```

## 依赖更新

1. 定期执行**依赖更新**，优先处理安全公告与主版本升级。
2. 启用 **Dependabot**：

```bash
gh api -X PUT repos/<owner>/<repo>/vulnerability-alerts
```

在仓库根目录添加 `.github/dependabot.yml`：

```yaml
version: 2
updates:
  - package-ecosystem: npm
    directory: /
    schedule:
      interval: weekly
    open-pull-requests-limit: 5
  - package-ecosystem: github-actions
    directory: /
    schedule:
      interval: monthly
```

3. Dependabot 策略建议：

| 场景 | 建议 |
| --- | --- |
| 补丁与次版本 | 允许自动合并，前提是 CI 通过且测试覆盖该路径 |
| 主版本升级 | 必须人工审核变更说明与破坏性变更 |
| 有安全公告 | 优先处理，记录处置结论 |
| 长期无维护的依赖 | 评估替换，写入决策记录 |

4. 更新后核验：锁文件变化范围合理、CI 通过（L4）、本地关键路径可运行（L1/L2）。
5. 不要为了「更新而更新」批量升级全部依赖，也不要在一次 PR 中混入多个主版本升级。

## CODEOWNERS

1. 多人协作或需要明确归属时，在 `.github/CODEOWNERS` 中声明路径负责人：

```text
*                       @owner
/docs/                  @owner
/CHANGELOG.md           @owner
/.github/workflows/     @owner
```

以上四行依次表示：全局默认负责人、文档目录、更新日志、工作流配置。

2. 个人项目也建议保留最小 **CODEOWNERS**，让后续接手的人知道谁决策。
3. 规则按「后面的规则覆盖前面的规则」生效；通配规则放在最前面，具体规则放在后面。
4. 启用必需审查时注意：单人多账号容易把自己挡在门外，需与分支保护规则一起确认。
5. 核验规则是否生效属于 L3 远程 API；文件内容属于 L1 静态。

## 安全维护

1. 每次公开或发布前重新执行敏感信息扫描，检查新增文件、CI 配置与示例数据。
2. 保持 `SECURITY.md` 可用：说明支持版本范围与私密报告渠道。
3. 开启 GitHub 的依赖漏洞告警、Secret scanning（可用时）与推送保护；不可用的功能不要声称已开启。
4. 疑似泄漏的处置顺序：先报告并建议轮换密钥，再讨论历史清理；清理历史属于危险操作，需单项授权。

## 归档

1. **归档**使仓库变为只读，保留历史与 issue 记录，是放弃维护时的推荐做法，而不是删除仓库。
2. 归档前确认：
   1. 没有未合并的 pull request 或悬空的发布准备。
   2. README 顶部注明项目状态与替代方案（如有）。
   3. 依赖告警与安全策略已给出最终处置说明。
   4. 最后一次发布说明中标注停止维护的原因与时间。
3. 归档操作由用户在网页 `Settings` 中完成，或经单项授权后执行：

```bash
gh repo archive <owner>/<repo> --yes
```

4. 归档不是删除。需要删除仓库时，走下面的危险操作流程。
5. 归档后仍要更新项目状态文件，把「维护中」标记为「已归档」。

## 门禁与危险操作边界

| 边界 | 规则 |
| --- | --- |
| 危险操作单项授权 | 删除仓库、更改可见性、批量关闭 issue 或 PR、删除 tag 或 Release、历史重写、`force push` 必须逐项说明目标、影响范围、不可逆后果与备份方式，并取得用户对该项的单独授权 |
| 一次授权范围 | 一次授权只对当次目标有效，不扩展到其他危险操作，也不构成长期授权 |
| 不得代替用户提交 | 代理可准备内容与命令，但推送、合并、关闭、发布、归档、删除由用户确认后执行 |
| 归档 | 优先归档而不是删除；归档前必须完成状态说明 |
| 可见性 | 不擅自公开私有内容，也不擅自把公开仓库改回私有 |
| 凭据 | 维护过程不索取、不记录、不回显密码、PAT、私钥、双因素验证码 |
| 「发布方案确认」 | 维护中若产生新的发布，仍需重新走发布方案确认门禁 |
