# 阶段 3「合规」执行手册

本手册是四阶段状态机（接入 / 建仓 / 合规 / 发布）中**阶段 3「合规」**的执行细则。目标是把一个「能跑」的仓库，补齐成陌生人能看懂、能复用、能安全提 issue 的公开仓库，并把仓库设置层面的安全能力开到合理档位。

合规阶段是**只读优先**的：先体检、再报告、再按分级补齐。任何写入动作都必须先经过用户确认；任何涉及仓库设置且不可逆的动作（改默认分支、改可见性、删除分支、关闭议题）按「危险操作单项授权」处理。

## 适用范围

| 项目 | 说明 |
| --- | --- |
| 进入条件 | 阶段 2「建仓」已完成，远程仓库已存在，本地与远程都已有默认分支。 |
| 退出条件 | `体检报告` 中「阻塞」项清零，进入阶段 4「发布」。 |
| 不处理 | 版本号决策、tag、GitHub Release（属于阶段 4，见 [release-stage.md](release-stage.md)）。 |
| 不处理 | 凭据获取与授权（属于阶段 1，见 [auth-and-safety.md](auth-and-safety.md)）。 |
| 前置读取 | 若 `docs/github/` 已初始化，先读 [state-persistence.md](state-persistence.md) 并与现状对齐。 |

## 步骤 1：运行只读体检

1. 确认项目根目录绝对路径，并在仓库根目录执行：

   ```bash
   python scripts/repo_doctor.py <project-root>
   ```

   本仓库内的脚本位置为 [repo_doctor.py](../scripts/repo_doctor.py)。

2. `repo_doctor.py` 只做只读检查，不修改任何文件、不调用写接口。它输出结构化清单，每一条包含：检查项、结论、命中的路径、建议动作。
3. 体检结论的四个等级固定为 **阻塞 / 建议 / 可选 / 通过**，不得自造等级词。
4. 脚本不可用时不要跳过体检：按本手册「步骤 2」到「步骤 6」逐项手工核对，并在报告里注明「脚本未运行，结论来自人工核对」。
5. 体检产生的所有结论都属于 **证据等级 L1 静态**。不要把它写成「远程已配置」——文件存在不等于仓库设置已生效。

## 步骤 2：文件级合规清单

按下表逐项判定。**必要性**列的含义：阻塞 = 公开仓库必须补齐才可发布；建议 = 应当补齐；可选 = 视项目类型。

| 检查项 | 必要性 | 判定标准 | 证据等级 |
| --- | --- | --- | --- |
| `README.md` | 阻塞 | 存在于仓库根目录或 `.github/`，且能回答「是什么、解决什么问题、如何安装、如何运行、如何贡献、许可证是什么」 | L1 静态 |
| `LICENSE` | 阻塞 | 根目录存在完整许可证正文，类型与用户在阶段 1 选定的许可证一致 | L1 静态 |
| `CONTRIBUTING.md` | 建议 | 根目录、`docs/` 或 `.github/` 存在，说明如何提交改动、分支与提交信息约定、如何跑测试 | L1 静态 |
| `CODE_OF_CONDUCT.md` | 建议 | 根目录或 `.github/` 存在，包含可用的举报渠道；不得保留 `[INSERT CONTACT METHOD]` 一类占位符 | L1 静态 |
| `SECURITY.md` | 建议 | 根目录或 `.github/` 存在，说明支持哪些版本、如何私下报告漏洞、响应预期 | L1 静态 |
| `Issue 模板` | 建议 | `.github/ISSUE_TEMPLATE/` 下存在 `.md` 或 `.yml`，且带有合法的 `name:` 与 `about:`（或 `description:`）字段 | L1 静态 |
| `Pull Request 模板` | 建议 | 根目录、`docs/` 或 `.github/` 下存在 `pull_request_template.md`（文件名不区分大小写） | L1 静态 |
| `CHANGELOG.md` | 建议 | 存在且新版本条目在最上方；格式参考 [Keep a Changelog](https://keepachangelog.com/zh-CN/1.1.0/) | L1 静态 |
| `.gitignore` | 阻塞 | 覆盖当前技术栈的依赖目录、构建产物、本地环境文件、日志与缓存 | L1 静态 |
| CI 工作流 | 建议 | `.github/workflows/` 下存在至少一个工作流，且运行成功 | L4 CI |
| 许可证文件命名 | 可选 | 统一使用 `LICENSE`；若用 `LICENSE.md` 或 `LICENSE.txt`，确保与清单文件中的声明一致 | L1 静态 |

补充规则：

1. `Issue 模板` 与 `Pull Request 模板` 只有位于默认分支才生效；在其他分支上创建不会出现在新建 issue / PR 页面。
2. 社区文件也可以放在账号级的 `.github` 仓库作为默认值，但个人项目建议直接放在项目内，避免排查时分不清来源。
3. 缺失项一律先记录，再逐条询问用户是否补齐；不得因为「反正是小项目」而擅自判定为「通过」。

## 步骤 3：README 内容审查

`README.md` 是唯一「阻塞」级别的文档项。按以下顺序核对：

1. **一句话定位**：首段能让完全不了解项目的人说出「这是什么」。
2. **问题与场景**：说明解决什么问题、适合谁用、不适合谁用。
3. **安装**：命令可直接复制执行，包含前置依赖与最低版本。
4. **运行 / 使用**：给出最小可运行示例，而不是只列函数名。
5. **贡献入口**：链接到 `CONTRIBUTING.md`，并说明 issue / PR 的基本要求。
6. **许可证**：显式写出许可证名称，例如「本项目基于 MIT 许可证发布，详见 [LICENSE](../LICENSE)」。
7. **禁止项**：不得出现空话占位段落（如「更多内容敬请期待」），不得保留模板生成器留下的原样文字，不得把个人邮箱、手机号、内网地址写进公开 README。
8. **徽章**：徽章为可选；若添加 CI 状态徽章，必须指向真实存在的工作流文件，否则算作错误信息。

## 步骤 4：许可证与兼容性

### 4.1 一致性检查

1. 读取 `LICENSE` 正文，识别 SPDX 标识符（如 `MIT`、`Apache-2.0`、`GPL-3.0-only`）。
2. 与用户在阶段 1 确认的许可证比对。**不一致时以用户选择为准并修正文件**，不得自行更改许可证类型、年份或版权归属人。
3. 检查清单文件中的声明是否一致：`package.json` 的 `license` 字段、`pyproject.toml` 的 `license`、`Cargo.toml` 的 `license` 等。出现多个来源时全部列出，由用户决定收敛方向。
4. 无许可证 ≠ 公共领域。若仓库没有任何许可证，结论为「保留全部权利」，并按「阻塞」处理（用户明确表示暂不授权也需在 `体检报告` 中记录该决定）。

### 4.2 许可证兼容

**许可证兼容**指项目依赖的许可证是否允许与项目自身许可证组合分发。检查方法：

1. 枚举直接依赖与间接依赖的许可证标识。
2. 重点识别传染性（copyleft）依赖：`GPL-2.0`、`GPL-3.0`、`AGPL-3.0`、`LGPL-*`、`MPL-2.0` 等。
3. 按下列常识对照表给出结论，并把结论标注为**建议**而非法律意见：

| 你的项目许可证 | 引入 GPL-3.0 依赖 | 引入 Apache-2.0 依赖 | 引入 MIT 依赖 |
| --- | --- | --- | --- |
| MIT | 冲突风险高，整体分发可能需按 GPL-3.0 释出 | 可以，保留 NOTICE 与许可声明 | 可以，保留版权与许可声明 |
| Apache-2.0 | 冲突风险高 | 可以，保留 NOTICE | 可以 |
| GPL-3.0 | 可以（Apache-2.0 与 GPL-3.0 单向兼容） | 可以 | 可以 |
| 无许可证 | 不可分发，需先确定自身许可证 | 不可分发 | 不可分发 |

4. GitHub 的依赖图可以辅助查看依赖许可证，结论记为 **证据等级 L3 远程 API**；本地的 `LICENSE` 与包清单结论记为 **L1 静态**。
5. 涉及商业分发、专利、商标或用户所在司法辖区的问题，明确告知「这需要法律意见，我无法替代」，并停止推断。

## 步骤 5：仓库设置审查

逐项检查，能通过 API 完成的优先通过 API 完成；不能的给出网页端编号步骤，由用户在浏览器中操作。每一步都要说明「为什么需要」。

| 设置项 | 建议值 | 为什么需要 | 典型证据等级 |
| --- | --- | --- | --- |
| 默认分支 | 与本地当前分支一致（通常 `main`） | 社区文件、模板、CI 默认都从默认分支读取 | L3 远程 API |
| `分支保护` | 保护默认分支：禁止强制推送、禁止删除、要求 PR 才能合并 | 阻止误操作重置历史；历史重写属于危险操作，应先有保护再讨论例外 | L3 远程 API |
| 议题开关 | 需要协作时开启 Issues | 关闭后用户无法报告问题，且社区健康文件中的模板不会生效 | L3 远程 API |
| `Dependabot` | 开启告警；按需开启安全更新或版本更新 | 依赖存在已知漏洞时能主动提示，而不是等用户发现 | L3 远程 API |
| `secret scanning` | 公开仓库开启告警与推送保护 | 在密钥进入远程历史前拦截；这是推送前本地扫描之外的第二道防线 | L3 远程 API |
| 仓库描述与主题 | 填写简短描述与 3-8 个 topics | 影响可发现性，也影响 README 摘要的呈现 | L3 远程 API |
| 允许的合并方式 | 个人项目建议只保留 Squash 与 Rebase | 保持线性历史，便于生成 CHANGELOG 与 Release 说明 | L3 远程 API |

关于 `secret scanning`：推送保护只能拦截 GitHub 已知的密钥格式，不能替代推送前的本地敏感信息扫描，也不能发现自定义格式的凭据。已经推送成功的密钥必须按「轮换优先」处理，历史清理属于危险操作，需要「危险操作单项授权」。

关于 `Dependabot`：告警本身不改代码。开启「版本更新」会自动开 PR，需要用户接受持续噪音；对个人项目建议先只开告警与安全更新。

## 步骤 6：CI 工作流审查

1. 检查 `.github/workflows/` 下每个工作流：触发条件、运行环境、步骤是否与项目技术栈匹配。
2. CI 只做**只读校验与构建**（安装依赖、跑测试、跑 lint、打包产物）。不要在 CI 中引入需要用户秘密的写操作，除非用户已在仓库 Secrets 中配置并明确授权。
3. 检查工作流是否引用了不存在的脚本、不存在的分支名、写错的工作流文件名。
4. 检查是否使用了过期的 action 主版本，或把 `permissions` 留空导致默认权限过宽；建议显式声明最小 `permissions`。
5. 检查工作流中是否硬编码了任何看起来像凭据的字符串。命中即按敏感信息处理，报告并建议轮换，不得直接提交修复。
6. 工作流的实际运行结论记为 **证据等级 L4 CI**。本地能跑通不等于 CI 通过。

## 步骤 7：输出体检报告

`体检报告` 是本阶段的唯一交付物，写入 `docs/github/`（结构见 [state-persistence.md](state-persistence.md)），同时在回复中给用户摘要。格式固定：

```markdown
## 体检报告

- 体检时间：<yyyy-MM-dd>
- 仓库：<owner>/<repo>
- 体检方式：repo_doctor.py / 人工核对
- 默认分支：<branch>

### 阻塞（必须清零才可发布）

| 编号 | 检查项 | 现状 | 证据等级 | 建议动作 | 需用户确认 |
| --- | --- | --- | --- | --- | --- |
| B-1 | LICENSE | 根目录缺失 | L1 静态 | 按用户选定的 MIT 写入 LICENSE | 是 |

### 建议

| 编号 | 检查项 | 现状 | 证据等级 | 建议动作 |
| --- | --- | --- | --- | --- |
| S-1 | SECURITY.md | 缺失 | L1 静态 | 添加漏洞报告渠道与支持版本 |

### 可选

| 编号 | 检查项 | 现状 | 证据等级 | 建议动作 |
| --- | --- | --- | --- | --- |
| O-1 | 变更日志 | 缺失 | L1 静态 | 首次发布前建立 CHANGELOG.md |

### 通过

| 编号 | 检查项 | 结论 | 证据等级 |
| --- | --- | --- | --- |
| P-1 | .gitignore | 覆盖依赖、构建产物、环境文件 | L1 静态 |
```

写报告时的硬性规则：

1. 每一条结论都必须带**证据等级**（L1 静态 / L2 本地 Git / L3 远程 API / L4 CI / L5 发布物），低等级不得冒充高等级。
2. 「通过」不等于「远程已配置」。文件级通过只给 L1；仓库设置通过必须拿到 L3。
3. 不得编造检查结果。无法核验的项写「未核验」并说明原因，不要猜。
4. 分级固定使用 阻塞 / 建议 / 可选 / 通过，不要新增「严重」「紧急」等词。
5. 每条「阻塞」项都要给出一个可执行的补齐动作，并标注是否需要用户先做决定（例如选许可证、确认公开范围）。

## 阻塞项清零与阶段流转

1. 「阻塞」项未清零前，不进入阶段 4「发布」，也不创建 tag 或 Release。
2. 用户明确拒绝处理某一阻塞项时，把该决定写入 `decisions.md`，并在 `progress.md` 中记录为「已知阻塞，用户接受风险」，同时在报告里保留该条，不得删除。
3. 每完成一次补齐，重新运行 `repo_doctor.py` 并更新体检报告编号与结论，不保留过期结论。
4. 补齐动作全部完成后：
   - 更新 `docs/github/progress.md`，写入本阶段完成事实；
   - 把影响后续维护的决定写入 `docs/github/decisions.md`（例如「暂不开启 Dependabot 版本更新」）；
   - 运行 `python scripts/validate_project_state.py <project-root>` 校验状态文件一致性（见 [state-persistence.md](state-persistence.md)）；
   - 向用户报告：当前阶段、阻塞是否清零、唯一下一步。

## 常见误判

| 误判 | 纠正 |
| --- | --- |
| 「本地有 LICENSE 文件，所以合规了」 | 只有 L1 证据。类型是否与用户选择一致、依赖许可证是否兼容仍需单独核对。 |
| 「CI 配置写好了就算通过」 | 配置存在是 L1，运行成功是 L4。 |
| 「仓库开起来默认就有分支保护」 | 个人仓库默认没有。必须实际查询后按 L3 结论记录。 |
| 「`secret scanning` 开着就不会泄漏密钥」 | 它只覆盖已知格式，且只在推送时拦截；自定义凭据仍需本地扫描。 |
| 「README 写个标题就够」 | 不能回答安装、运行、贡献、许可证四问的 README 视为未通过。 |
