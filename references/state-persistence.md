# 项目状态持久化约定

本约定规定 `manage-github-projects` 如何把项目进展落盘到被管理的仓库里。核心原则：**以仓库文件而不是聊天记忆作为事实来源**。跨会话、跨工具、换一个 agent 接手时，状态文件是唯一的续接依据。

状态文件统一存放在被管理项目的 `docs/github/` 目录下，由本 Skill 提供的脚本初始化与校验。

## 目标与原则

1. **可续接**：任何人在任何时间读到这六个文件，都能说出当前处于四阶段（接入 / 建仓 / 合规 / 发布）的哪一步、本地与远程分别是什么状态、唯一下一步做什么。
2. **事实优先**：文件中记录的是「已发生的事实」与「已确认的决定」，不是计划中的愿望。未完成事项必须带状态标记，不得写成已完成。
3. **不存秘密**：状态文件是普通文本，会被提交进仓库并可能公开。任何秘密信息都不得写入。
4. **单一事实来源**：版本号、默认分支名、可见性、许可证等关键值只在一处定义（`project-plan.md`），其他地方引用而不复制。
5. **冲突即报告**：状态文件之间、状态文件与 `git` 实际输出之间出现矛盾时，先列出冲突再更新事实，不得选择性忽略。

## 目录与文件布局

初始化后，被管理项目的目录结构如下：

```text
<project-root>/
├── docs/
│   └── github/
│       ├── project-plan.md
│       ├── progress.md
│       ├── decisions.md
│       ├── version-change.md
│       ├── test-report.md
│       └── release-checklist.md
└── ...（项目自身文件）
```

硬性规则：

1. **`docs/github/`** 是固定路径，不要改名为 `docs/GitHub/`、`.github-docs/` 或其他形式；脚本按此路径定位文件。
2. 这六个文件都属于项目文档，会被提交到仓库。因此它们天然是公开可见的（对公开仓库而言）。
3. 访问私有信息时不要写入这些文件；改为在对话中向用户索取并只在当次使用。
4. 文件不存在时不要凭空手写一份「看起来很像」的替代品；用脚本初始化，再按需修改内容。

## 六个文件的用途

| 文件 | 用途 | 主要更新时机 | 关键字段 |
| --- | --- | --- | --- |
| `project-plan.md` | 记录项目的基本设定：仓库归属与名称、默认分支、可见性、许可证、技术栈、项目根路径、依赖概览。是**非秘密标识**的唯一定义处。 | 接入阶段通过「公开范围确认」后首次写入；后续仅在设定变更时更新。 | 仓库全名、默认分支、可见性、许可证、技术栈、本地路径 |
| `progress.md` | 记录四阶段状态机的推进情况：当前阶段、已完成事项、进行中事项、阻塞项、唯一下一步。 | 每次用户确认、拒绝、跳过或报告阻塞后立即更新。 | 当前阶段、整体进度、已完成、阻塞、下一步 |
| `decisions.md` | 记录重要选择的决策日志：决定了什么、为什么、备选方案是什么、由谁确认。 | 用户做出不可轻易回退的选择时（选许可证、选可见性、跳过某阻塞项、授权危险操作）。 | 日期、决定、理由、备选、确认人、是否可逆 |
| `version-change.md` | 版本变更单：本次版本号、变更类型（新增/修复/破坏性）、面向用户的变更列表、目标 tag 名、是否预发布。 | 进入发布阶段、执行「发布方案确认」前生成；发布完成后归档为该版本的记录。 | 版本号、变更类型、变更条目、tag 名、预发布标记 |
| `test-report.md` | 验证记录：执行了哪些检查、命令与结果、结论、对应的**证据等级**。 | 每次完成合规体检、发布前核验或修复后复验时更新。 | 检查项、命令、结果、证据等级、时间 |
| `release-checklist.md` | 发布前逐项勾选清单：版本号一致性、tag 与提交对应、CHANGELOG 更新、Release 说明、附件可用性。 | 发布阶段逐项勾选；发布后回填核验结果。 | 检查项、状态、证据等级、核验人 |

### 写入内容细则

**project-plan.md**

```markdown
## 项目计划

- 仓库全名：<owner>/<repo>
- 本地路径：<absolute-or-relative-path>
- 默认分支：main
- 可见性：public / private
- 许可证：MIT / Apache-2.0 / GPL-3.0-only / 未决定
- 技术栈：<例如 Node.js 20 + TypeScript>
- 主要依赖来源：<例如 npm、PyPI>
- 公开范围：<将公开的文件类型与排除路径摘要>
- 最后更新：<yyyy-MM-dd>
```

**progress.md**

```markdown
## 进度

- 当前阶段：<接入 | 建仓 | 合规 | 发布>（第 n/4 阶段）
- 整体进度：<简短比例或已完成项数>
- 最后更新：<yyyy-MM-dd>

### 已完成

- [x] <事实，标注证据等级与日期>

### 进行中

- [ ] <事项>（阻塞原因：<无 / 具体原因>）

### 阻塞

- [ ] <阻塞项>（影响：<阻塞什么>；处置：<等待用户决定 / 等待外部条件>）

### 下一步

- <唯一的一件事，可验证>
```

**decisions.md**

```markdown
## 决策日志

### <yyyy-MM-dd> 选择 MIT 许可证

- 决定：采用 MIT
- 理由：用户希望被商业项目广泛采用，且不要求衍生作品开源
- 备选：Apache-2.0（多专利授权条款）、GPL-3.0（要求衍生作品开源）
- 确认人：<用户名>
- 可逆性：可逆，但需同步更新 LICENSE、清单文件与 README
```

**version-change.md**

```markdown
## 版本变更单

- 当前版本：<上一个已发布版本或「无」>
- 目标版本：<x.y.z>
- 变更类型：新增 / 修复 / 破坏性
- tag 名：<例如 v1.2.0>
- 预发布：是 / 否
- 计划发布日期：<yyyy-MM-dd>

### 面向用户的变更

- 新增：<条目>
- 修复：<条目>
- 破坏性变更：<条目或「无」>

### 版本号一致性

| 来源 | 值 | 是否一致 |
| --- | --- | --- |
| 目标 tag |  |  |
| 清单文件（`package.json` 等） |  |  |
| CHANGELOG 顶部条目 |  |  |
| Release 标题 |  |  |
```

**test-report.md**

```markdown
## 验证记录

| 时间 | 检查项 | 命令 | 结果 | 证据等级 |
| --- | --- | --- | --- | --- |
| <yyyy-MM-dd> | 本地工作区干净 | `git status --short` | 无输出 | L2 本地 Git |
| <yyyy-MM-dd> | 远程已存在该分支 | GitHub API 查询 | 存在 | L3 远程 API |
```

**release-checklist.md**

```markdown
## 发布前检查清单

- [ ] 版本号在 tag / 清单文件 / CHANGELOG / Release 标题四处一致
- [ ] CHANGELOG 已包含本版本全部面向用户的变更
- [ ] 工作区干净，所有变更已提交并推送
- [ ] `体检报告` 中「阻塞」项已清零
- [ ] tag 使用带注解的 tag 且已推送到远程
- [ ] Release 说明来自实际变更，未编造功能
- [ ] Release 页面可访问，tag 与提交对应
- [ ] Release 附件已实际下载验证可用
```

## 初始化方式

1. 初始化有前置条件：用户已通过「公开范围确认」，并同意建立项目记录。
2. 在仓库根目录执行：

   ```bash
   python scripts/init_project_state.py <project-root>
   ```

   本仓库内的脚本位置为 [init_project_state.py](../scripts/init_project_state.py)。

3. 脚本行为约定：
   - 在 `<project-root>/docs/github/` 下创建六个模板文件；
   - **不覆盖已存在的文件**，已存在时跳过并在输出中说明；
   - 不写入任何秘密信息，模板中只包含占位说明与空字段；
   - 只做文件创建，不执行任何 `git` 写操作，也不调用远程 API。
4. 初始化完成后，立即用用户已确认的内容填充 `project-plan.md`，并在 `progress.md` 中写入当时阶段。
5. 初始化属于文件创建操作，不需要危险操作授权；但如果 `docs/github/` 已存在同名文件，先读取确认内容再决定是否手工合并，不要绕过脚本的跳过逻辑强行覆盖。

## 校验方式

1. 每次恢复会话、接手已有仓库、或在合规/发布阶段开始前执行：

   ```bash
   python scripts/validate_project_state.py <project-root>
   ```

   本仓库内的脚本位置为 [validate_project_state.py](../scripts/validate_project_state.py)。

2. 校验范围：

   | 校验项 | 期望 |
   | --- | --- |
   | 目录存在 | `docs/github/` 存在 |
   | 六个文件齐全 | `project-plan.md`、`progress.md`、`decisions.md`、`version-change.md`、`test-report.md`、`release-checklist.md` 均存在 |
   | 必填字段非空 | `project-plan.md` 中的仓库全名、默认分支、可见性、许可证有值 |
   | 阶段合法 | `progress.md` 中的当前阶段属于「接入 / 建仓 / 合规 / 发布」之一 |
   | 敏感信息扫描 | 六个文件中不含疑似凭据、密码、私钥或验证码字样的内容 |
   | 引用一致 | 文件名引用与实际存在的文件名一致 |

3. 校验是**只读**的：不会修正文件，也不会删除内容。
4. 校验失败时的处理顺序：
   1. 逐条列出失败项与命中位置；
   2. 判断是「缺失」「内容不合规」还是「状态矛盾」；
   3. 缺失或不合规时，向用户说明并请求确认后补齐；
   4. 状态矛盾时先列出冲突来源（文件 vs 文件、文件 vs `git` 实际输出），再更新事实，不得直接改成一个「看起来合理」的值。
5. 校验结论按**证据等级**标注：文件存在性与内容检查属于 L1 静态；若结论牵涉远程状态，必须另行获取 L3 远程 API 证据，不能沿用 L1。

## 更新时机

| 触发事件 | 必须更新的文件 |
| --- | --- |
| 通过「公开范围确认」 | `project-plan.md`、`progress.md` |
| 通过「首推范围确认」 | `progress.md` |
| 通过「发布方案确认」 | `version-change.md`、`progress.md` |
| 用户确认 / 拒绝 / 跳过某项事项 | `progress.md`；重要选择追加到 `decisions.md` |
| 完成一次合规体检或发布核验 | `test-report.md`；勾选项回填到 `release-checklist.md` |
| 授权并执行了危险操作 | `decisions.md`（记录授权范围与结果）、`progress.md` |
| 出现阻塞 | `progress.md`（阻塞项 + 影响 + 处置方式） |
| 许可证、可见性、默认分支等设定变更 | `project-plan.md`、`decisions.md` |

更新规则：

1. 只追加或就地修正事实，不删除历史决策记录。
2. 每条事实带日期；跨阶段的结论带证据等级。
3. 不把「计划做」写成「已完成」；计划项放在「进行中」并标注状态。
4. 每次更新后重新运行校验，确保引用与阶段字段仍然合法。

## 禁止记录密码与敏感信息禁写清单

**禁止记录密码**及任何等价秘密。以下内容一律不得写入 `docs/github/` 下的任何文件、提交信息、分支名、tag 名、Release 说明、issue 或 PR 正文：

| 禁止写入 | 说明 |
| --- | --- |
| token | 包括 personal access token、OAuth token、GitHub App 安装令牌、CI 临时令牌 |
| 密码 | 账号密码、数据库口令、服务登录口令、Wi-Fi 口令 |
| 私钥 | SSH 私钥、签名私钥、证书私钥、部署密钥内容 |
| 验证码 | 双因素验证码、短信码、恢复码、备份码 |
| 个人证件 | 身份证件号码、护照号、社保号、银行卡号、驾照号 |
| 其他个人敏感信息 | 真实住址、私人手机号、私人邮箱、未公开的健康或财务信息 |
| 连接串 | 含用户名与口令的数据库 / 消息队列连接字符串 |
| 内部地址 | 未公开的内网主机名、内网 IP、私有仓库地址 |

允许写入的内容是**非秘密标识**：

| 允许写入 | 示例 |
| --- | --- |
| 仓库标识 | `<owner>/<repo>` |
| 分支名 | `main`、`release/1.x` |
| 可见性 | `public`、`private` |
| 许可证标识符 | `MIT`、`Apache-2.0`、`GPL-3.0-only` |
| 版本号与 tag 名 | `1.2.0`、`v1.2.0` |
| 技术栈与依赖名 | `Node.js 20`、`express` |
| 公开的账号用户名 | GitHub 用户名（本身是公开信息） |
| 路径 | 项目根目录、关键文件相对路径 |
| 公开的链接 | 仓库 URL、Actions 运行链接、Release 链接 |

判定方法：如果一条信息泄漏后能让别人**以你的身份访问某个资源**，它就是秘密，禁止写入；如果它只是**指向某个公开或已授权资源**，它就是非秘密标识，可以写入。

发现状态文件中已经写入了秘密时：立即报告命中位置，建议**轮换**该凭据，并说明历史清理属于危险操作、需要「危险操作单项授权」，不要自行改写历史。

## 冲突处理清单

恢复会话时发现下列矛盾，按对应处理：

| 矛盾 | 处理 |
| --- | --- |
| `progress.md` 说已推送，但 `git status` 显示有未推送提交 | 以 `git` 实际输出为准（L2），更新文件并说明冲突 |
| `project-plan.md` 写的默认分支与远程默认分支不一致 | 以远程为准（L3），更新文件并记录到 `decisions.md` |
| `version-change.md` 的版本号与 CHANGELOG 顶部不一致 | 停止发布，列出两处值，请用户决定收敛方向 |
| `release-checklist.md` 已勾选但缺少对应证据 | 撤销勾选并标注「证据缺失」，重新核验 |
| 文件中的许可证与 `LICENSE` 正文不一致 | 以用户确认的选择为准，修正文件与正文，并记录决定 |
