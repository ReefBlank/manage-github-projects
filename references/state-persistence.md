# 项目状态持久化约定

本约定规定 `manage-github-projects` 如何把项目进展落盘到被管理的仓库里。核心原则：**以仓库文件而不是聊天记忆作为事实来源**。跨会话、换工具、换执行者接手时，状态文件是唯一的续接依据。

状态文件统一存放在被管理项目的 `docs/github/` 目录下，模板由本 Skill 的 `assets/project-docs/` 提供，由脚本初始化与校验。

## 目标与原则

1. **可续接**：任何人读到这六个文件，都能说出当前处于四阶段（接入 / 建仓 / 合规 / 发布）的哪一步、本地与远程分别是什么状态、唯一下一步做什么。
2. **事实优先**：记录「已发生的事实」与「已确认的决定」，不写愿望。未完成事项必须带状态标记，不得写成已完成。
3. **不存秘密**：状态文件是普通文本，会被提交进仓库并可能公开。任何秘密信息都不得写入。
4. **单一事实来源**：仓库名、默认分支、可见性、许可证等关键值只在一处定义（`project-plan.md`），其他地方引用而不复制。
5. **证据分级**：跨阶段的结论必须标注**证据等级**（L1 静态 / L2 本地 Git / L3 远程 API / L4 CI / L5 发布物），低等级不得冒充高等级。
6. **冲突即报告**：状态文件之间、状态文件与 `git` 实际输出之间出现矛盾时，先列出冲突再更新事实，不得选择性忽略。

## 目录与文件布局

初始化后，被管理项目的目录结构如下：

```text
<project-root>/
├── docs/
│   └── github/
│       ├── project-plan.md
│       ├── progress.md
│       ├── decisions.md
│       ├── version-change.md
│       ├── test-report.md
│       └── release-checklist.md
└── ...（项目自身文件）
```

硬性规则：

1. **`docs/github/`** 是固定路径。不要改名为 `docs/GitHub/`、`.github-docs/` 或其他形式，脚本按此路径定位文件。
2. 这六个文件都是项目文档，会被提交到仓库，因此对公开仓库而言天然公开可见。
3. 需要保密的信息不要写入这些文件；改为在对话中向用户索取并只在当次使用。
4. 文件不存在时不要凭空手写一份「看起来很像」的替代品：先用脚本从模板初始化，再按实际情况填写。
5. 每个状态文件必须以单个 `# ` 一级标题开头（校验脚本会强制检查这一条），正文用 `##` 分节。

## 六个文件的用途

| 文件 | 模板标题 | 用途 | 主要更新时机 |
| --- | --- | --- | --- |
| `project-plan.md` | 项目规划 | 记录项目的基本设定与首版范围：本地路径、仓库名、归属账号/组织、可见性、许可证、默认分支、公开范围、合规基线、发布规划。是**非秘密标识**的唯一定义处。 | 接入阶段通过「公开范围确认」后首次填写；设定变更时更新。 |
| `progress.md` | 进度 | 记录四阶段状态机的推进情况：当前阶段、整体进度、本地状态、远程状态、门禁记录、各阶段检查项、阻塞项、证据等级与未验证项。 | 每次用户确认、拒绝、跳过或报告阻塞后立即更新。 |
| `decisions.md` | 决策记录 | 决策日志：每条写清「选了什么、为什么、放弃了什么、何时需要复查」，并记录危险操作的单项授权情况。 | 用户做出不可轻易回退的选择时；授权或跳过危险操作时。 |
| `version-change.md` | 版本变更单 | 版本决策与变更记录：版本号、tag 名、目标提交、是否预发布、版本号一致性表、变更内容、兼容性影响、回滚方案、发布后核验。 | 进入发布阶段、执行「发布方案确认」前填写。 |
| `test-report.md` | 测试报告 | 验证记录：环境、执行过的命令与结果、仓库体检结论、未验证项及其影响、是否可进入发布阶段。 | 每次完成合规体检、发布前核验或修复后复验时更新。 |
| `release-checklist.md` | 发布检查清单 | 发布前逐项勾选：门禁、内容与合规、安全、版本与发布物、证据等级汇总、发布后动作。 | 发布阶段逐项勾选；发布后回填核验结果。 |

### 各文件的关键字段

**`project-plan.md`**

| 分区 | 内容要点 |
| --- | --- |
| 基本信息 | 本地路径、仓库名、归属账号 / 组织、可见性、许可证、默认分支、目标平台，每项带状态（已确认 / 待确认） |
| 首版范围 | 一句话定位、面向谁、解决什么问题、首版必须做、明确不做 |
| 公开范围 | 源码、构建产物、本地配置与密钥、大文件、内部文档各自的处理方式与依据 |
| 合规基线 | `README.md`、`LICENSE`、`CONTRIBUTING.md`、`CODE_OF_CONDUCT.md`、`SECURITY.md`、Issue / Pull Request 模板、`CHANGELOG.md`、CI 工作流、分支保护与 Dependabot 的勾选状态 |
| 发布规划 | 版本、计划内容、状态 |
| 未确认项与风险 | 待用户决定或待外部条件的事项 |

**`progress.md`**

| 分区 | 内容要点 |
| --- | --- |
| 当前状态 | 当前阶段、整体进度、本地状态、远程状态、当前版本、唯一下一步 |
| 门禁记录 | 四道门禁（目标信息收齐 / 公开范围确认 / 首推范围确认 / 发布方案确认）各自的状态、时间与备注 |
| 阶段 1-4 | 各阶段的检查项清单 |
| 阻塞项 | 描述、影响、处理方向、状态 |
| 证据等级与未验证项 | 结论、证据等级、说明 |

**`decisions.md`**

| 分区 | 内容要点 |
| --- | --- |
| 决策列表 | 按 `D001`、`D002`… 编号，预设仓库可见性、许可证、默认分支名、大文件与产物策略、版本与发布节奏五个常见决策位，每条含决策、原因、放弃的选项、复查条件 |
| 危险操作授权记录 | 操作、目标、用户是否单项授权、时间、结果；预置 `force push`、历史重写、删除仓库、更改可见性、删除 tag / Release 五行 |

**`version-change.md`**

| 分区 | 内容要点 |
| --- | --- |
| 版本信息 | 版本号、tag 名、目标提交、是否预发布、计划发布时间 |
| 版本号一致性 | `git tag`、`package.json`（或等价清单）、`CHANGELOG.md` 顶部条目、GitHub Release 标题四处对照 |
| 变更内容 | 新增、修复、破坏性变更 |
| 兼容性影响 | 受影响的使用方式、迁移步骤 |
| 回滚方案 | 回滚目标版本、回滚命令、回滚后需要通知的对象 |
| 发布后核验 | Release 页面可访问、tag 指向预期提交、附件可下载 |

**`test-report.md`**

| 分区 | 内容要点 |
| --- | --- |
| 环境 | 操作系统、运行时版本、依赖来源、测试日期 |
| 执行记录 | 编号、命令 / 场景、结果、证据等级 |
| 仓库体检 | `scripts/repo_doctor.py` 阻塞项数量、敏感信息扫描、体积体检 |
| 未验证项 | 未验证内容、原因、影响 |
| 结论 | 证据等级汇总、是否可以进入发布阶段、剩余阻塞 |

**`release-checklist.md`**

| 分区 | 内容要点 |
| --- | --- |
| 门禁 | 「发布方案确认」已由用户明确回复；版本号一致性检查通过 |
| 内容与合规 | README 四问可答；LICENSE 与用户选定类型一致；CHANGELOG 与实变更一致；社区文件齐备；CI 结论为通过 |
| 安全 | 敏感信息扫描无命中；工作区干净；危险操作已安全跳过或已取得单项授权并记录 |
| 版本与发布物 | 带注解 tag 已推送；Release 已创建且预发布已勾选；说明来自实际变更；附件可下载 |
| 证据等级汇总 | 本地状态 L2、远程状态 L3、CI 的 L4、发布物的 L5 |
| 发布后 | 记录时间与版本号到 `progress.md`；更新 `decisions.md`；规划下一个版本 |

模板源文件位于仓库的 [assets/project-docs/](../assets/project-docs/)，共六个 `.md`。修改模板时以该目录为准，不要在文档里维护第二份模板正文。

## 初始化方式

1. 初始化有前置条件：用户已通过「公开范围确认」，并同意建立项目记录。
2. 在 Skill 仓库根目录执行：

   ```bash
   python scripts/init_project_state.py <project-root>
   ```

   脚本位置：[init_project_state.py](../scripts/init_project_state.py)。

3. 脚本实际的执行结果：

   | 情况 | 输出 | 退出码 |
   | --- | --- | --- |
   | 正常创建 | 每个文件一行 `CREATE: <路径>`，末行 `OK: N file(s) created under <路径>` | 0 |
   | 目标文件已存在 | 该文件一行 `SKIP: <路径>`，其余照常创建 | 0 |
   | 项目目录不存在 | `ERROR: project directory does not exist: <路径>` | 1 |
   | 模板目录缺失 | `ERROR: template directory is missing: <路径>` | 1 |

4. 行为约定：
   - 把 `assets/project-docs/` 下的六个 `.md` 复制到 `<project-root>/docs/github/`；
   - `docs/github/` 不存在时自动创建（等价于 `mkdir -p`）；
   - **不覆盖已存在的文件**，只跳过；
   - 不写入任何秘密信息；
   - 只做文件创建，不执行任何 `git` 写操作，也不调用远程 API。
5. 初始化完成后，立即用用户已确认的内容填写 `project-plan.md`，并把当时阶段写入 `progress.md`。
6. 文件已存在时不要绕过跳过逻辑强行覆盖：先读取现有内容，判断是「已填写」还是「仍是空模板」，再与用户确认后手工合并。

## 校验方式

1. 每次恢复会话、接手已有仓库，或在合规 / 发布阶段开始前执行：

   ```bash
   python scripts/validate_project_state.py <project-root>
   ```

   脚本位置：[validate_project_state.py](../scripts/validate_project_state.py)。加 `--strict` 可把未完成占位符也当作错误。

2. 校验是**只读**的：不修正文件、不删除内容、不访问网络。
3. 校验范围：

   | 校验项 | 判定 | 输出前缀 |
   | --- | --- | --- |
   | `docs/github/` 存在 | 不存在则报错并提示先运行 `init_project_state.py` | `ERROR:` |
   | 六个文件齐全 | 缺少 `project-plan.md`、`progress.md`、`decisions.md`、`version-change.md`、`test-report.md`、`release-checklist.md` 中任一项即报错 | `ERROR:` |
   | 每个文件以 H1 开头 | 去除前导空白后必须以 `# ` 开头 | `ERROR:` |
   | 疑似真实凭据 | 命中 GitHub token、`github_pat_` 形式令牌、`AKIA` 形式的 AWS 密钥、`-----BEGIN ... PRIVATE KEY-----` 私钥块、`sk-` 形式的接口密钥等模式 | `ERROR:` |
   | 未完成占位标记 | 文件中仍含常见的未完成标记词（英文全大写缩写与中文提示词各一类，以脚本内的检查列表为准）；默认仅提示，`--strict` 时升级为错误 | `NOTE:` |

4. 退出码：无错误返回 0（有 `NOTE` 时打印 `OK with N note(s)`）；存在错误时逐条打印 `ERROR:` 并以 `FAILED: N error(s)` 结束，返回 1。
5. 校验失败时的处理顺序：
   1. 逐条列出失败项与命中位置（文件名与行号）；
   2. 判断是「缺失」「内容不合规」还是「状态矛盾」；
   3. 缺失或不合规时，向用户说明并请求确认后补齐；
   4. 状态矛盾时先列出冲突来源（文件 vs 文件、文件 vs `git` 实际输出），再更新事实，不得直接改成一个「看起来合理」的值。
6. 文件存在性与内容检查的结论属于 L1 静态；若结论牵涉远程状态，必须另行获取 L3 远程 API 证据，不能沿用 L1。

## 更新时机

| 触发事件 | 必须更新的文件 |
| --- | --- |
| 通过「目标信息收齐」 | `project-plan.md`（基本信息）、`progress.md`（门禁记录） |
| 通过「公开范围确认」 | `project-plan.md`（公开范围）、`progress.md` |
| 通过「首推范围确认」 | `progress.md` |
| 通过「发布方案确认」 | `version-change.md`、`progress.md` |
| 用户确认 / 拒绝 / 跳过某项事项 | `progress.md`；重要选择追加到 `decisions.md` |
| 完成一次合规体检或发布核验 | `test-report.md`；勾选项回填到 `release-checklist.md` |
| 授权并执行了危险操作 | `decisions.md`（授权记录表）、`progress.md` |
| 出现阻塞 | `progress.md`（阻塞项 + 影响 + 处理方向） |
| 许可证、可见性、默认分支等设定变更 | `project-plan.md`、`decisions.md` |
| 发布完成 | `progress.md`、`decisions.md`、`release-checklist.md` |

更新规则：

1. 只追加或就地修正事实，不删除历史决策记录。
2. 每条事实带日期；跨阶段的结论带证据等级。
3. 不把「计划做」写成「已完成」；计划项放在进行中并标注状态。
4. 每次更新后重新运行校验，确保结构与内容仍然合法。

## 禁止记录密码与敏感信息禁写清单

**禁止记录密码**及任何等价秘密。以下内容一律不得写入 `docs/github/` 下的任何文件，也不得写入提交信息、分支名、tag 名、Release 说明、issue 或 PR 正文：

| 禁止写入 | 说明 |
| --- | --- |
| token | 包括 personal access token、OAuth token、GitHub App 安装令牌、CI 临时令牌 |
| 密码 | 账号密码、数据库口令、服务登录口令、压缩包口令 |
| 私钥 | SSH 私钥、签名私钥、证书私钥、部署密钥内容 |
| 验证码 | 双因素验证码、短信码、恢复码、备份码 |
| 个人证件 | 身份证件号码、护照号、社保号、银行卡号、驾照号 |
| 其他个人敏感信息 | 真实住址、私人手机号、私人邮箱、未公开的健康或财务信息 |
| 连接串 | 含用户名与口令的数据库 / 消息队列连接字符串 |
| 内部地址 | 未公开的内网主机名、内网 IP、私有仓库地址 |

允许写入的内容是**非秘密标识**：

| 允许写入 | 示例 |
| --- | --- |
| 仓库标识 | `<owner>/<repo>` |
| 分支名 | `main`、`release/1.x` |
| 可见性 | `public`、`private` |
| 许可证标识符 | `MIT`、`Apache-2.0`、`GPL-3.0-only` |
| 版本号与 tag 名 | `1.2.0`、`v1.2.0` |
| 技术栈与依赖名 | `Node.js 20`、`express` |
| 公开的账号用户名 | GitHub 用户名（本身是公开信息） |
| 路径 | 项目根目录、关键文件相对路径 |
| 公开的链接 | 仓库 URL、Actions 运行链接、Release 链接 |

判定方法：如果一条信息泄漏后能让别人**以你的身份访问某个资源**，它就是秘密，禁止写入；如果它只是**指向某个公开或已授权资源**，它就是非秘密标识，可以写入。

发现状态文件中已经写入了秘密时：立即报告命中位置，建议**轮换**该凭据，并说明历史清理属于危险操作、需要「危险操作单项授权」，不要自行改写历史。处置顺序见 [auth-and-safety.md](auth-and-safety.md)。

## 冲突处理清单

恢复会话时发现下列矛盾，按对应处理：

| 矛盾 | 处理 |
| --- | --- |
| `progress.md` 说已推送，但 `git status` 显示有未推送提交 | 以 `git` 实际输出为准（L2），更新文件并说明冲突 |
| `project-plan.md` 写的默认分支与远程默认分支不一致 | 以远程为准（L3），更新文件并记录到 `decisions.md` |
| `version-change.md` 的版本号与 CHANGELOG 顶部不一致 | 停止发布，列出两处值，请用户决定收敛方向 |
| `release-checklist.md` 已勾选但缺少对应证据 | 撤销勾选并标注「证据缺失」，重新核验 |
| 文件中的许可证与 `LICENSE` 正文不一致 | 以用户确认的选择为准，修正文件与正文，并记录决定 |
| `progress.md` 的当前阶段不在四阶段之内 | 视为损坏，按实际 `git` 与远程状态重新判定阶段，并记录修正原因 |
