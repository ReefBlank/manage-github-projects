# 阶段 1「接入」凭据与安全手册

本手册是四阶段状态机（接入 / 建仓 / 合规 / 发布）中**阶段 1「接入」**的凭据处理与安全操作细则。接入阶段只做三件事：确认账号与仓库归属、确认**凭据**能力范围、确认公开范围与许可证。**本阶段不创建任何远程资源。**

所有涉及凭据的动作遵循一条总原则：**只探测能力，不接触秘密**。

## 一、三条不可越过的红线

1. **不索取密码**：不要求用户提供 GitHub 账号密码，也不要求用户提供邮箱密码、仓库密码或任何平台的登录口令。
2. **不索取验证码**：不要求用户提供双因素验证码（TOTP / 短信码）、恢复码、备份码、设备验证码或安全问题答案。
3. **不索取、不回显、不记录秘密凭据**：包括但不限于 personal access token、SSH 私钥内容、OAuth 客户端密钥、签名密钥、CI 部署密钥。

由此派生的强制约束：

- **凭据只从用户已配置的环境读取**：通过 Git 凭据助手、GitHub CLI 的既有登录状态、SSH agent 等既有通道使用凭据，而不是让用户在对话里粘贴明文。
- **不得把 token 写入仓库**：不得写入任何被 Git 跟踪的文件、`.env`（示例文件除外且只能用假值）、提交信息、分支名、tag 名、Release 说明、issue 正文或 PR 描述。
- **报告凭据能力时必须脱敏**：只描述「有 / 无 / 覆盖范围」。
- **不代替用户完成登录、双因素、OAuth 授权、删除确认和付费操作**。这些步骤一律由用户本人在官方页面完成。
- **危险操作默认安全跳过**：未获得针对该项操作的明确单项授权前，不执行任何一条危险操作，也不「顺便」执行。

## 二、凭据类型与推荐使用方式

| 凭据类型 | 用途 | 推荐读取方式 | 允许在本机命令中出现明文 |
| --- | --- | --- | --- |
| `credential.helper`（Git 凭据助手） | HTTPS 推送与拉取 | 由 Git 自动调用，本手册只查询配置值 | 否 |
| `personal access token` | GitHub REST API、HTTPS 替代密码、CLI 认证 | 由凭据助手、环境变量或 CLI 自身存储提供 | 否 |
| `SSH` 密钥 | `git@github.com:` 形式的推送与拉取 | 由 SSH agent 提供，本手册只验证连通性 | 否 |
| GitHub CLI 登录态 | 创建仓库、查询 API、发 Release | `gh auth status` 读取登录状态与作用域 | 否 |
| Git 提交身份 | 提交作者信息 | `git config user.name` / `user.email` | 是（非秘密） |
| 仓库 Secrets | CI 中的自动化凭据 | 由用户在仓库设置中配置，代理不读取其值 | 否 |

关键区分：

- **`personal access token` 与密码同等敏感**。它一旦泄漏，持有者就获得了该账号被授予的全部权限。优先建议用户采用细粒度 token，并把权限限制到具体仓库与最小集合。
- 细粒度 token 有功能缺口（例如不是所有端点都支持、部分组织场景不可用），此时再考虑经典 token，但必须缩短有效期。
- `SSH` 私钥比 token 更敏感：它可能没有有效期，且不易被平台自动吊销。私钥文件永不读取、永不复制、永不粘贴。

## 三、只探测不读取：允许与禁止的命令

### 3.1 允许执行的探测命令

| 目的 | 命令 | 输出中是否可能含秘密 |
| --- | --- | --- |
| 查询是否配置了凭据助手 | `git config --get credential.helper` | 否（只返回助手名称） |
| 查询凭据助手（含全局/系统层） | `git config --show-origin --get-all credential.helper` | 否 |
| 查询用户名（不取密码） | `git credential fill`（仅取 `username=` 一行，禁止输出 `password=`） | 是，必须截断处理 |
| 查询 GitHub CLI 登录状态 | `gh auth status` | 否（返回账号与作用域） |
| 验证 SSH 连通性 | `ssh -T git@github.com` | 否（返回用户名与认证成功信息） |
| 查看 SSH agent 已加载的密钥指纹 | `ssh-add -l` | 否（只返回指纹与备注） |
| 查询提交身份 | `git config user.name` / `git config user.email` | 否 |
| 查询远程地址 | `git remote -v` | 否（注意：带 token 的 URL 会泄漏，见下） |

`git credential fill` 属于**有条件允许**：它由 Git 自己解析凭据助手，可能把密码返回给标准输出。使用时必须满足：

1. 只用于判断「该主机是否已有可用凭据」，不做其他用途；
2. 不把完整输出写进对话、日志或文件；
3. 只报告「用户名 X 的凭据可用，作用域包含 repo」这类**脱敏**结论；
4. 若输出中出现 `password=` 字段，直接丢弃，只在内部判断其是否存在。

### 3.2 禁止执行的命令（不得以任何理由运行）

| 禁止命令 | 风险 |
| --- | --- |
| `echo $GITHUB_TOKEN` / `echo $GH_TOKEN` / `printenv` | 直接把 token 明文打到对话里 |
| `cat ~/.ssh/id_rsa`、`cat ~/.ssh/id_ed25519`、`cat ~/.netrc` | 泄漏私钥或长期凭据 |
| `git remote -v` 中带 `https://user:token@...` 的 URL 原样回显 | 泄漏 token |
| `git config --list`（全量输出） | 可能输出 `http.*.extraheader`、URL 中内嵌的凭据 |
| 把 `.env`、`credentials.json`、`.npmrc`、`.pypirc` 内容贴出来 | 泄漏凭据 |
| 任何要求用户「把 token 发给我」的表述 | 直接违反红线 |

如果某条命令已经执行并把疑似秘密输出到了对话中：立即停止其他动作，告知用户该值应视为已泄漏，建议**轮换**，并且不要再复述该值。

### 3.3 远程地址的规范化

1. 使用 HTTPS 时，远程地址不应内嵌用户名与 token：

   ```bash
   git remote set-url origin https://github.com/<owner>/<repo>.git
   ```

2. 使用 SSH 时：

   ```bash
   git remote set-url origin git@github.com:<owner>/<repo>.git
   ```

3. 发现远程 URL 已内嵌凭据时：先报告，再建议改为不含凭据的地址，然后提醒用户轮换该凭据（因为旧值可能已进入 shell 历史、`~/.gitconfig` 或某个备份）。

## 四、最小权限

**最小权限**的目的是缩小凭据泄漏后的爆炸半径。给用户的建议（标注为建议，由用户决定）：

1. 优先使用**细粒度 personal access token**，并把仓库范围限制到当前要操作的那一个仓库。
2. 按任务逐项授予权限，例如：

   | 任务 | 需要的权限（细粒度） |
   | --- | --- |
   | 只读体检、查询仓库状态 | 仓库的 Metadata 读取 |
   | 创建仓库 | 目标账号的仓库创建权限 |
   | 推送代码 | 仓库的 Contents 写入 |
   | 创建 Release / tag | 仓库的 Contents 写入 |
   | 修改分支保护、议题开关 | 仓库的 Administration 写入 |

3. 设置合理的过期时间；一次性任务可以设很短，长期使用建议不超过 90 天并定期轮换。
4. 不要在多个项目之间复用同一个 token；一个项目一个 token，便于单独吊销。
5. 不要给 `personal access token` 授予管理员级别的作用域，除非当前任务确实需要。
6. 组织仓库可能要求管理员审批细粒度 token，提前说明这一点，避免用户以为失败是配置错误。

## 五、脱敏报告模板

每次报告凭据能力，使用下列固定格式，禁止自由发挥：

```text
凭据探测结果（脱敏）
- HTTPS 凭据助手：<名称 / 未配置>
- 已检测到可用凭据：<是 / 否>
- 归属账号：<用户名>
- 作用域覆盖：<例如 repo、workflow / 未知>
- SSH：<agent 已加载 n 个密钥，连通性验证通过 / 未配置 / 未验证>
- GitHub CLI：<已登录，账号 X / 未安装 / 未登录>
- 结论：<当前任务是否具备所需能力>
```

硬性规则：

1. 任何凭据字段一律写作 `<已配置 / 未配置>` 或 `<作用域列表>`，不输出任何片段、长度、前后缀或哈希。
2. 不输出 token 的字符数，不输出「前 4 位是 ghp_」这类描述。
3. 用户主动粘贴了凭据时：不转述、不确认内容、不写入任何文件，直接提示「请立即在 GitHub 设置中吊销并重新生成」，然后继续流程。
4. 报告「作用域未知」时不得推测权限；要么进一步用只读 API 验证，要么明确写「未验证」。

## 六、危险操作默认安全跳过

以下操作**默认安全跳过**：即使它们在技术上能让流程更快，也不在没有获得**单项授权**的情况下执行。

| 危险操作 | 不可逆后果 | 备份方式 |
| --- | --- | --- |
| `force push` | 覆盖远程历史，他人已拉取的提交与本地未推送的改动画失 | 先 `git push --mirror` 到备份远程，或本地完整克隆 |
| 历史重写（`git filter-repo` 等） | 所有相关提交哈希改变，签名失效，打开的 PR diff 报废 | 完整本地克隆 + 备份分支；先关闭或合并所有打开的 PR |
| 删除仓库 | 仓库、issue、PR、Release、Actions 记录全部消失，恢复受限且有窗口期 | 完整镜像克隆 + Release 附件单独下载 |
| 更改可见性 | 私有转公开可能一次性暴露全部历史内容；公开转私有会破坏外部引用 | 公开前完成敏感信息扫描与体积检查 |
| 删除 tag 或 Release | 已发布的下载链接与依赖该 tag 的构建失效 | 记录 tag 指向的提交哈希与附件清单 |
| 清空 / 强推远程分支 | 该分支上所有未合并的工作丢失 | 备份分支 + 记录原提交哈希 |
| 批量关闭 issue / PR | 丢失待处理上下文，通知噪声大 | 先导出列表并说明关闭原因 |

执行前必须向用户说明四件事，缺一不可：

1. **目标**：具体针对哪个仓库、哪个分支、哪个 tag、哪个提交范围。
2. **影响范围**：哪些分支/标签/协作者/自动化会受影响，是否会触发其他流水线。
3. **不可逆后果**：哪些内容无法通过正常手段恢复。
4. **备份方式**：执行前需要落地的备份步骤，以及如何验证备份可用。

### 单项授权模板

```text
【危险操作单项授权】
操作：<force push / 历史重写 / 删除仓库 / 更改可见性 / 删除 tag / 删除 Release / 批量关闭 issue>
目标：<owner>/<repo>，分支 <branch>，范围 <具体提交或 tag>
影响范围：<列出受影响的分支、标签、协作者、自动化>
不可逆后果：<明确写出>
已完成的备份：<备份位置与验证方式>
本次授权仅覆盖上述操作，不扩展到其他危险操作，也不长期有效。

请回复「确认执行该操作」以继续；回复其他内容则中止并保留现状。
```

授权规则：

1. 一次授权只覆盖**一个具体操作、一个具体目标、一个具体时间点**。
2. 不因为用户此前授权过 `force push` 就默认可以执行删除 tag。
3. 用户回复泛化词（「好的」「可以」「继续」）不等于授权，必须重复说明并等待明确确认。
4. 执行后立即核验并报告结果，核验证据需标注**证据等级**（例如远程分支头哈希为 L3 远程 API，本地提交为 L2 本地 Git）。

## 七、凭据泄漏处置与轮换

发现疑似泄漏（本地扫描命中、`secret scanning` 告警、用户误粘贴）时，按固定顺序处理：

1. **立即报告**：说明命中位置（文件路径与行号，或告警编号）、凭据类型、可能的暴露范围。不要复述命中内容本身。
2. **先轮换，后清理**：优先在 GitHub 设置中吊销并重新生成凭据。已吊销的密钥不再具有访问能力，这通常已经解决了主要风险。
3. **再评估历史清理**：历史清理需要重写提交，属于危险操作，必须走「危险操作单项授权」。同时提醒用户：任何克隆过的副本、缓存视图、fork 都可能有残留。
4. **检查相邻风险**：该凭据是否曾出现在 CI 日志、Release 附件、issue 正文、Gist 或构建产物中。
5. **记录决定**：把泄漏事件、处理方式与残余风险写入 `docs/github/decisions.md`（见 [state-persistence.md](state-persistence.md)），但**不写入凭据本身**。
6. **加固**：补充 `.gitignore` 规则、在 CI 中改用平台提供的临时凭据、必要时启用推送保护。

**轮换**清单（逐项确认）：

| 项 | 动作 |
| --- | --- |
| personal access token | 在 GitHub 设置中吊销旧 token 并生成新 token，更新本机凭据助手存储 |
| SSH 密钥 | 从账号中移除旧公钥，在 `~/.ssh/authorized_keys` 与部署密钥中同步清理，生成新密钥对 |
| 仓库 Secrets | 在仓库设置中替换为新值，并检查工作流引用名称是否变化 |
| 部署密钥 / GitHub App | 吊销并按最小权限重建 |
| 凭据助手缓存 | 清除本机旧凭据条目，避免继续使用已吊销的 token |

## 八、接入阶段的操作顺序

1. 执行「目标信息收齐」门禁：只问 3-5 个会改变路线的问题（本地项目路径、期望仓库名、可见性倾向、许可证倾向、是否已有远程）。
2. 按第三章执行只读探测，按第五章格式输出**脱敏**结果。
3. 确认仓库归属与命名：个人账号还是组织；仓库名是否符合 GitHub 命名规则；是否已存在同名仓库（先查再建）。
4. 确认可见性，并明确「公开是一次不可逆的信息披露」；未获用户明确表示前不建议公开。
5. 确认许可证倾向，给出候选与影响（例如 MIT 宽松、Apache-2.0 含专利授权、GPL-3.0 具传染性），并标注为建议。
6. 输出公开范围清单：将公开的文件类型、将排除的路径、需要用户自行判断的灰色地带。
7. 等待用户明确回复「公开范围确认」。泛化回复不通过门禁。
8. 用户通过门禁后，才允许进入阶段 2「建仓」。
